## §6.1.23 client requirement traceability

| Catalog requirement ID | Normative source and obligation | Implementation | Verification |
| --- | --- | --- | --- |
| `KMIPKIT-REQ-SPEC-6.1.23-001-001` | Specification §6.1.23: a client SHALL NOT use a Usage-Limited object for protection unless an allocation has been obtained | Successful-allocation context in `crates/kmipkit-client/src/usage_allocation.rs` and typed guard in `crates/kmipkit-client/src/execute.rs`; bindings expose the same context and guarded calls; Baseline profile mapping in `crates/kmipkit-protocol/src/profile.rs` remains caller-owned; literal ID Placeholder is not accepted as a resolved object identifier. | Rust `usage_allocation_guard_tests::unsuccessful_pending_malformed_and_nonpositive_allocations_cannot_create_contexts` and `usage_allocation_cannot_bind_the_id_placeholder_as_an_object_identifier`; compiled C mTLS guarded Encrypt consumer; Java TLS guard test; Python native mTLS guarded Encrypt and over-budget rejection; profile mapping `profile_maps_usage_allocation_before_protection_as_caller_owned_prohibition`. Callers must route applicable use through the selected context. |
| `KMIPKIT-REQ-SPEC-6.1.23-001-002` | §6.1.23: request allocation only after Activation Date and before Protect Stop Date | The caller supplies timing knowledge; KMIPKit does not infer remote dates. `crates/kmipkit-protocol/src/profile.rs` maps the Baseline date window without an evaluator; the boundary is documented in the approved scope and API documentation. | No remote-date validation is fabricated. The profile test `profile_maps_usage_allocation_date_window_as_caller_owned_required_behavior` verifies the static mapping; documentation and client contract leave timing and unguarded/external use to the caller and server. |
| `KMIPKIT-REQ-SPEC-6.1.23-002-001` | §6.1.23/Table 232: include required number of Usage Limits Units | Typed request requires a Long Integer and preserves the exact signed count and raw unit in the caller-supplied context; `crates/kmipkit-protocol/src/profile.rs` maps Usage Limits Count as required. | Rust exact-count/wire tests and guard constructor boundaries; C ABI metadata getters; Java and Python creation tests verify exact count and raw unit; profile test `profile_maps_get_usage_allocation_required_usage_limits_count`; invalid local input is NotSent and the encoded request preserves the count. |
| `KMIPKIT-REQ-SPEC-6.1.23-002-002` | §6.1.23: do not continue after the entire allocation has been consumed until another allocation is obtained | The local guard reserves cost before typed Encrypt, MAC, or Sign; it rolls back only on proven `NotSent` and retains reservations after ambiguous or completed outcomes. `crates/kmipkit-protocol/src/profile.rs` maps the Baseline prohibition as caller-owned; accounting remains local. | Rust exact-budget, over-budget, identifier/operation boundary, asynchronous, and delivery-state tests; compiled C consumer observes reserved/available units after mTLS Encrypt; Java mTLS verifies exact balance and mismatch rejection; Python native mTLS proves over-budget rejection opens no extra exchange; profile test `profile_maps_consumed_allocation_restriction_as_caller_owned_prohibition`. Exact balance is accepted, over-budget use is rejected without transport, proven NotSent releases the reservation, and possibly delivered outcomes retain it. |

The guard covers only typed Encrypt, MAC, and Sign calls routed through one caller-owned instance. It does not count Decrypt, MAC Verify, Signature Verify, Hash, unguarded/raw requests, other processes, or external server use. It never reports local reservation as remote consumption.

The four §6.1.23 catalog requirements are recorded as `scoped_verified`: KMIPKit enforces the caller-supplied allocation context and cost for guarded typed protection calls, while object timing and use outside those calls remain caller/server responsibilities. This status is limited to the documented client boundary and is not a profile-conformance claim.

KMIPKIT-0010 T053 maps all four §6.1.23 profile obligations: allocation before protection, the Activation Date/Protect Stop Date request window, required Usage Limits Count, and non-use after allocation consumption. The count rule verifies the required request field; the other three mappings leave remote timing, allocation availability, and consumed state caller-owned. These tests verify the profile categories and boundaries, not remote state or calls outside the explicit guard. Exact test IDs are `profile_maps_usage_allocation_before_protection_as_caller_owned_prohibition`, `profile_maps_usage_allocation_date_window_as_caller_owned_required_behavior`, `profile_maps_get_usage_allocation_required_usage_limits_count`, and `profile_maps_consumed_allocation_restriction_as_caller_owned_prohibition` in `crates/kmipkit-protocol/tests/support/profile_unit.rs`.
