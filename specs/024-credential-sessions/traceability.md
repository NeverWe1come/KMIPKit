## KMIPKIT-0043 T045 — Delegated Login binding parity

The Rust API exposes `ClientRequest::delegated_login`, `DelegatedLoginRequest` with optional typed Lease Time, Request Count, and generic Usage Limits, and a typed response whose Ticket retains raw Ticket Type, secret Ticket Value, and the complete ordered generic Ticket structure. The C ABI requires a generic Rights handle, accepts the Table 199 scalar forms, returns Ticket Value as a span borrowed from the response-item handle, and returns a caller-owned generic Ticket TTLV copy. Java and Python expose equivalent request forms and typed response accessors; each response wrapper owns and wipes its internal Ticket Value copy and releases its generic TTLV copy on close. Java callers receive independent `byte[]` copies and must protect and clear them; Python callers receive immutable `bytes` copies that the runtime cannot deterministically clear. All layers redact secret bytes from diagnostic formatting and preserve unknown Ticket Type values, unknown Ticket children, and their original order.

The common batch result continues to expose Table 201 Result Status, Result Reason, Result Message, outcome, delivery state, and response evidence. Delegated Login mapping does not translate a server failure into a success or retry the operation. The exact four-language declaration mapping and Red/Green/Refactor verification are recorded under T045 in `specs/043-public-api-bindings/traceability.md` and `implementation-evidence.md`.

## Requirement handling

The approved spec records no separate catalog client normative clause IDs for these three operations. Payload requiredness and result-table alternatives are mapped above to stable operation/tag IDs and spec-scoped table IDs. Server-side permission enforcement described in operation prose remains server behavior; this client exposes caller-controlled payloads and preserves returned results without claiming the server accepted a right or ticket.
