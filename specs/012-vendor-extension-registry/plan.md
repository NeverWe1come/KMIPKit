# KMIP 2.1 Vendor Extension Registry Implementation Plan

> **For agentic workers:** Execute tasks in tasks.md with strict Red, Green, Refactor commits. This feature requires independent security and QA reviews before its draft PR is ready.

**Goal:** Add a per-client immutable KMIP 2.1 vendor extension registry with schema-validated typed values and equivalent Rust, C, Java, and Python capabilities.

**Architecture:** Keep protocol schema/value types in kmipkit-protocol and immutable registry ownership in kmipkit-client. Generate mechanical public declarations and adapter surfaces from the reviewed API manifest, while keeping validation logic and idiomatic language facades handwritten and reviewed. Preserve KMIPKIT-0007 criticality behavior and ADR-0012's private typed request/zeroizing transport boundary.

**Tech Stack:** Rust 2024/MSRV 1.94, C ABI, Java 17/JNI with Gradle Kotlin DSL, Python 3.12/CFFI with Maturin, Python standard-library generator.

**Spec:** specs/012-vendor-extension-registry/spec.md

## Global Constraints

- KMIP version 2.1 and TTLV are the only 1.0 protocol/encoding.
- Registry state is immutable and client-owned; no global mutable state or transport/TLS access.
- Data-only schema vocabulary only; no callbacks, scripts, regex engine, dynamic executable plugins, raw body, or generic Item bypass at Client::execute.
- Preserve unknown tags, enum values, bitmask bits, field multiplicity, and order.
- Apply TTLV limits of 16 MiB, depth 64, and 100,000 elements before/while validation.
- Enforce every ExtensionRegistryLimits default and hard maximum in spec.md before clone/reserve/allocation: definitions, schema nodes, child rules, metadata bytes, discriminator scalar bytes, constraint-member counts, payload-index entries, lookup comparisons, and depths. Callers may raise or lower each default up to its hard maximum; fields whose defaults equal their hard maxima cannot be raised. Count every declared schema node and constraint member even if a caller reuses a builder value. Count UTF-8 identity and Extension Information Text String bytes and exact discriminator Byte String bytes before copying.
- Compile each allowed-enumeration set into a sorted numeric index and binary-search it in at most 13 value comparisons. Represent ordering as directed tag edges, reject duplicate/self/cyclic edges at construction, and compile edge endpoints to child-rule indices. Validation records first/last positions for declared children in one input pass and checks each edge once afterward; each occurring `before_tag` must precede every `after_tag` occurrence. Never rescan all constraints for each repeated input item.
- For inbound lookup, first count and then build one bounded temporary tag index over at most 100,000 total payload Items including the root Structure, shared by every definition. Count at most one Structure descriptor per Structure and one `(tag, original child index)` pair per child, for at most 100,000 Structure descriptors plus 99,999 child pairs (199,999 index records) under the configured 200,000-record maximum. Tags are 24-bit, so use fixed-pass radix ordering; retain duplicate entries and preserve the source subtree and order. Resolve each path step with lower/upper-bound searches and require exactly one matching child. Charge each tag comparison to the configured lookup budget; limit exhaustion returns a stable redacted resource-limit error and no partial typed result. Hard bounds are at most 1,024 × 64 path steps, 35 child-tag comparisons per step, and 4,194,304 comparisons overall.
- No secrets in logs, errors, formatting, or default debug output; KMIPKit-owned secret memory follows zeroization rules.
- Rust unsafe remains in kmipkit-ffi only and each block has a SAFETY rationale.
- Stable C names use kmipkit_ and fixed-width types; all four public adapters have equivalent capabilities.
- Generated Rust/C/Java/Python outputs are committed and regenerated by a pinned repository tool; never edit output by hand.
- Exact pinned OASIS upstream sources remain immutable; no scraping or downloads.
- Human review/merge and pre-1.0 qualified security review remain required.

## Summary

Implement the 1.0 registry commitment as a sealed, data-only schema system. A registry definition declares vendor identity, extension name/version, compatibility, one finite discriminator, and a recursive TTLV schema. Client configuration validates and freezes definitions into a deterministic index. Incoming Message Extensions match by vendor plus exact discriminator, then undergo complete schema validation. Duplicate keys are rejected at registry construction, but distinct discriminator paths may both match one payload. Lookup collects exact discriminator matches before schema validation: zero matches or multiple matches remain unrecognized without selection; exactly one candidate proceeds to complete schema validation and becomes a typed view only after success, retaining the original generic subtree. Unrecognized content follows KMIPKIT-0007 criticality handling. Outbound values are admitted to the typed request path only through that schema-validated type.

The feature also establishes the first slice of `specification/api/public-api.json` and generated C/JNI/CFFI registry adapter declarations. Later approved API specifications extend this manifest and own the complete 1.0 API parity gate; KMIPKIT-0012 does not claim the manifest is the complete 1.0 API inventory.

## Design

### Data flow and ownership

1. Callers create ExtensionDefinition values using the supported typed builders in a client configuration.
2. Registry construction validates identifiers, compatibility, schema vocabulary, discriminator uniqueness, and resource constraints. It then freezes the registry and builds a deterministic discriminator index.
3. Outbound extension payloads are built as generic TTLV values or typed builder values, validated through the immutable client registry against one exact registered identity and its definition, and returned as a sealed `RegisteredExtensionValue`. A protocol-level `ValidatedExtensionValue` from a standalone definition is not request-admissible. The caller must provide a Criticality Indicator for each request use; no default is selected. Only the registry-scoped type, wrapped with the explicit indicator, can be attached repeatedly to a closed typed batch item, preserving caller order as allowed by §8.3/Table 396.
4. Client execution adds the standard Message Extension fields to that batch item and serializes through the existing private OperationEncodingPermit/zeroizing owner path from ADR-0012. The extension registry does not add an encoder or a production writer callsite.
5. On receive, the existing message model preserves the generic extension. The client builds one bounded temporary tag index for the received extension subtree and shares it across all definition paths. Each path step resolves only a unique matching child; absent or repeated tags are non-matches. Lookup stops after the second exact key hit. Zero hits yield an unrecognized generic value; multiple hits yield an ambiguous unrecognized generic value without schema selection; exactly one hit proceeds to complete schema validation and, on success, a typed view with borrowed access to the unchanged generic subtree.
6. Unknown, schema-invalid, or multiply-matching content has no partial typed view. Existing KMIPKIT-0007 criticality handling decides reject vs continue/preserve.
7. C, Java, and Python call generated opaque-handle surfaces. Their adapters never accept raw KMIP bodies at the typed execute entry point and map stable error codes without payload text.

### Data-only schema vocabulary

Define a sealed recursive schema grammar in kmipkit-protocol: expected TTLV value type; permitted child tags and cardinality; vendor-declared child-order constraints; string/octet length ranges; numeric ranges; accepted enum values; allowed/required bitmask bits; and an explicit policy for undeclared children. Discriminators are exact scalar comparisons reached by a bounded tag path. No arbitrary predicate, regex, script, callback, or extension code is evaluated. Structural and semantic rules not representable by this grammar remain unrecognized in 1.0 unless a later reviewed compiled-adapter specification adds support.

Schemas preserve input order in the source TTLV subtree. They validate only declared semantic rules; they do not sort, rewrite, discard, or normalize values. Extension processing shares configured TTLV limits.

### API manifest and generated surfaces

Create specification/api/public-api.json as the canonical manifest seed for registry records, opaque handles, stable C symbols, Java methods, Python methods, error categories, and ownership metadata. Add a versioned manifest schema and deterministic Python 3.12 standard-library generator with check mode. The manifest is intentionally partial: later API specifications add operations and other public types to the same source of truth. Generated outputs are committed and must not be hand-edited.

Handwritten implementation includes Rust schema validation, client registry integration, safety/error mapping, and idiomatic Java/Python facades. Generated output contains repetitive declarations, handle plumbing, and parity fixtures only. The manifest and generator must not scrape OASIS.

### Errors and security

Registry construction reports stable categories for invalid identity, duplicate key, compatibility mismatch, and invalid schema. Inbound lookup reports no-match, invalid-schema, or ambiguous-match outcomes; ambiguity means that distinct discriminator paths both matched for the vendor, and it never selects by registration order. Validation errors identify the rule/tag path without echoing actual values or payload bytes. Default Debug/Display on secret-bearing values is redacted. C ownership uses opaque handles and explicit create/retain/drop semantics. Java/Python copies are documented as runtime-owned and outside KMIPKit zeroization guarantees.

Schema matching has deterministic work: test no more than 1,024 registered discriminators and 64 path steps per definition, stop after a second exact key hit and return ambiguous-unrecognized, otherwise validate the bounded input subtree against the sole candidate. Definition count, aggregate schema nodes, per-Structure child rules, metadata bytes, and discriminator/schema depth have explicit defaults and hard maxima. Sorted child indexes bound each input child's rule lookup to at most 13 comparisons; the validator visits no more than the configured 100,000 input Items and 100,000 schema nodes. Definitions are supplied only by the local caller during client configuration; no untrusted network data can add registrations after client construction. Schema recursion is constrained by the configured depth and element limits.

### Integration boundaries

- KMIPKIT-0006 remains owner of MessageExtension generic structure and field order.
- KMIPKIT-0007 remains owner of unknown critical rejection and unknown non-critical preservation. The registry only reports recognition/typed view and never overrides the criticality action.
- Existing client execution remains the sole typed request send boundary and uses its existing secret-safe writer permit.
- Query Function Extension List/Map and Extension Information are modeled/exposed as deterministic metadata only; Query operation execution is deferred to its operation-family spec.
- No vendor-specific built-in schema is added absent an identified, approved vendor definition.
