## Advancement rule

When an owner draft receives direct human implementation authorization, record it as `authorized_wip` with exact evidence from that owner specification; do not change its formal status or claim acceptance. Such mappings are branch-only and fail the complete-release gate. When an owner becomes formally approved/accepted on the active release line, update the row and manifest dependency state; if the status is stale, record merged specification-PR evidence and the discrepancy in implementation evidence. For an unowned operation, first create and approve a separate operation specification, then link it here and in the normative catalog through its reviewed update. Every release-ready API still requires owner approval, canonical Rust support, all four mappings, and verification evidence. Do not use a draft worktree as the source of an API signature.
