# Research: Local Cosmian KMS Integration

## Decisions

### Use the binary KMIP socket

**Decision**: Connect to Cosmian's raw TCP socket using KMIP binary TTLV and TLS 1.3/mTLS through the production `kmipkit_client::Client` API.

**Rationale**: Cosmian documents a native KMIP socket that carries binary TTLV, while its HTTP KMIP API is a JSON TTLV API. KMIPKit 1.0's existing production raw-TLS transport is the matching path. The KMS 5.28.0 configuration supports a listener on `5696`, server PEM certificate/key, and a client CA.

**Sources**:

- Cosmian KMS 5.28.0 server configuration reference: [server_configuration_file.md](https://github.com/Cosmian/kms/blob/5.28.0/documentation/docs/configuration/server_configuration_file.md), database defaults at lines 171–196, TLS and KMIP socket settings at lines 197–233.
- Cosmian's [KMIP socket and JSON TTLV documentation](https://docs.cosmian.com/key_management_system/kmip_support/json_ttlv_api.html).
- KMIPKit production transport contract and TLS policy: `specs/013-production-transport/spec.md`, `specs/013-production-transport/plan.md`, and OASIS KMIP Profiles v2.1 Operating System Profile §5.3.1 items 3–4 as the existing profile context.

### Pin the local server and isolate it

**Decision**: Use `ghcr.io/cosmian/kms:5.28.0@sha256:7b60fd4484930969906caa5722b727054ff96d49339ce81e3c64ca9e4278540e` and `alpine:3.22.2@sha256:4b7ce07002c69e8f3d704a9c5d6fd3053be500b7f1c69fc0d80990c2ad8dd412`; run them only for local tests, publish KMIP port `5696` to `127.0.0.1`, use SQLite in the disposable container filesystem with database clearing enabled, and do not mount persistent KMS data.

**Rationale**: This makes the requested KMS version reproducible and keeps all mutations inside the disposable local service. The original bounded suite created server-side test objects and changed their metadata. The 2026-10-16 amendment additionally authorizes importing test-generated fixtures and destroying only unique objects created by the same case. Stopping and removing the container discards its database state.

### Generate temporary mutual-TLS credentials in Compose

**Decision**: A short-lived Alpine/OpenSSL Compose service creates a local CA and `localhost` server/client certificates in an ignored `.local/cosmian-kms/certs` directory, then exits successfully before KMS starts.

**Rationale**: Contributors do not need host OpenSSL, checked-in credentials, a secret manager, or an externally issued certificate. The root CA is supplied explicitly to KMIPKit and to Cosmian for client-certificate validation.

### Keep the first live test opt-in and narrow

**Decision**: Add one ignored test for the existing typed Discover Versions request. The user later authorized executing it while the KMIPKIT-0013 coverage blocker was still open.

**Rationale**: The branch already has production raw-TLS, mTLS, TTLV framing, typed request and typed response support for this one operation. OASIS KMIP Specification v2.1 §6.1.16, Tables 211–213, defines the operation and response; §9.16, Table 421, defines the Protocol Version structure. No broader operation support is required to test this vertical slice.

## Risks and limitations

- The GitHub container registry image must be reachable and the `5.28.0` image tag must be published for the contributor's platform.
- The initial smoke test covered only Discover Versions. The approved 2026-10-16 matrix expansion below replaces that original limitation; Task14 has run the complete serial ignored suite against the pinned digest, with unresolved case outcomes and the test summary recorded in the Task 6 report.
- This smoke test exercises one request/response on one implementation. It is not a conformance suite, full KMIP 2.1 compatibility result, or certification.
- TLS certificate files are generated as local ignored artifacts. Removing `.local/cosmian-kms` deletes those files; Compose can regenerate them on the next start.

## Initial live-test failure and diagnosis

The user later authorized the live test before KMIPKIT-0013's coverage gate was cleared. The first run reached the KMS over verified mTLS; Cosmian logged one `DiscoverVersions` request for `kmipkit-integration-client`. KMIPKit then returned a sanitized transport error with `ResponseStarted` and cause `Other`. Temporarily logging only the eight-byte TTLV response-header metadata showed `tag=0x42007b`, `type=0x01`, and `value_len=168`; the diagnostic code was removed immediately afterward. OASIS KMIP v2.1 §8.4, Table 397, defines Response Message as the root structure, and §11.56 assigns its tag `0x42007B`. The transport had been expecting `0x420078`, the Request Message tag. This identifies a KMIPKit response-frame validation defect rather than a missing Cosmian setting.

### Operation scope and disagreements

**Decision**: Enumerate the exact 35-path set in `spec.md` before implementation. Set Attribute and Modify Attribute have distinct typed requests and independent measured successes in the historical twenty-case run; retain the single published `Set Attribute (Modify)` grouping as source provenance. Query stays in the set with the known Table 283 required-field defect. Ping and Adjust Attribute remain separate unadvertised probes. The exhaustive live run classified both returned responses as malformed because the Batch Item omitted Operation (Status 1, Reason 4); do not reinterpret that as a well-formed unsupported response. [dispatch.rs](https://github.com/Cosmian/kms/blob/5.28.0/crate/server/src/core/operations/dispatch.rs) dispatches `ReCertify` although `support.md` marks Re-certify unimplemented: retain a separate safe typed discrepancy probe (OASIS §6.1.45, Tables 298–302), or explicit setup/client blocker, outside the advertised-success count.

**Disagreement policy**: Record both documentation and implementation citations. Retain standards-valid documented combinations even when source inspection predicts rejection; classify them as documented-but-source-gap and observe the live outcome. Add applicable source-only formats/parameters to the inventory without describing them as published promises. Standards-invalid combinations get source-backed exclusions rather than fabricated positive tests. A source comment claiming KMIP compliance cannot override the pinned normative text. Runtime outcome remains independent of expected classification.

### Import/Export formats, PFX and encoding

**Decision**: Test each applicable default and explicit format, with algorithm restrictions. Include PrivateKey/PKCS#12 PFX import: `objects.md` Notes advertises PFX, while [import.rs](https://github.com/Cosmian/kms/blob/5.28.0/crate/server/src/core/operations/import.rs) `process_private_key` selects `process_pkcs12`, which parses a `PrivateKey` Key Block and extracts linked private/public key, leaf certificate and optional chain. `formats.md` omits this path. Preserve that omission note in its matrix row, including links and cleanup ownership for every created object.

Inspect [export.rs](https://github.com/Cosmian/kms/blob/5.28.0/crate/server/src/core/operations/export.rs) and its delegated conversion helpers for other source-only formats, including PKCS7/PKCS12 legacy variants, transparent symmetric material and Secret Data/Opaque export. These are inventory candidates, not invented standard enumerations or evidence of a successful exchange. Capture exact source symbols, representation and operation applicability before accepting each row.

OASIS §11.25, Table 461 defines PKCS#12 `0x16` and PKCS#10 `0x17`; it does not define PEM or PKCS7 Key Format Type values. OASIS §2.1, Table 2 and §11.25, Table 460 require DER for certificates and DER-defined key formats. The vendor `formats.md` advertises PEM/DER, whereas `import.rs::process_certificate/process_pkcs12` uses DER parsing and key conversion paths must be checked individually. Keep fixture encoding, any normalization, actual wire format and documented-but-source-gap probes distinct; do not treat PEM text as a standard wire-format obligation. PEM *Certificate Request Type* is separately defined by §11.8, Table 439 and may apply to Certify input. Wrapping Encoding Option (§11.18, Tables 449–450) means No Encoding/TTLV Encoding, not PEM/DER.

- The RSA-OAEP/AES128-GCM example in `algorithms.md` and [encrypt.rs::encrypt_with_rsa](https://github.com/Cosmian/kms/blob/5.28.0/crate/server/src/core/operations/encrypt.rs) disagree on the request's algorithm selection. ### Test architecture, isolation and reporting

**Decision**: Keep `cosmian_kms` as the integration target and split family cases into focused modules. The JSON manifest is the versioned inventory. A stable row records FR links, operation/object, algorithm/parameters, format/encoding, setup, exact normative/vendor sources, expected outcome, test/family and actual result. Offline validators prove completeness and case-to-test parity; every network case remains ignored.

All supported paths and separate probes already have `ClientRequest` variants. Any unrepresentable required row is an explicit client blocker requiring separately approved production scope.

Run serially through the existing local runner, retain sanitized per-case outcomes, and tear down Compose even after failures; verify no running service remains. Historical eighteen-success evidence does not close any new row. The matrix and family runners are implemented; Task14 completed one full serial live run and verified empty Compose status, but failed cases and per-row observations still require reconciliation before the matrix is considered complete.

### Inventory representations

`encoding` is always binary TTLV. `fixture.encoding`, `fixture.normalization` and `fixture.wire_representation` distinguish file input from the typed message. Applicable ASN.1 fixtures have separate DER and PEM cases; PEM is decoded before typed Import/Register and exported DER is compared with the fixture. No PEM text is sent as certificate DER or DER-defined KeyMaterial. This excludes a standards-invalid wire interpretation of the vendor's broad PEM/DER statement while preserving that documentation discrepancy (§2.1/Table 2; §11.25/Tables 460–461). Certify's PEM Certificate Request Type is a separate legal request variant (§11.8/Table 439).

RSA PKCS#1/PKCS#8/transparent formats and EC PKCS#8/transparent/SEC1 formats are restricted to applicable keys/curves. PKCS#8 for public keys means SPKI in Cosmian; it is a documentation alias, not a new enumeration. SEC1 is not multiplied onto X25519/X448/EdDSA keys. Transparent structures and Raw proprietary key bytes are not ASN.1 PEM/DER variants. Explicit format selection and omitted Get/Export format fields are distinct. SecretData's omitted selection can preserve Opaque despite the table's Raw default.

PrivateKey/PKCS#12 import covers password/no password and optional chain branches. **`objects.md` advertises PFX; `formats.md` omits it.** `import.rs::process_private_key/process_pkcs12` extracts linked private/public key, leaf certificate and optional chain. Each row tracks every resulting object; the password link is secret and removed from retained attributes. Other compatible subject algorithms have container cases; password/chain branch behavior is independently represented with RSA-2048 rather than pretending it creates a new algorithm. Source-only PKCS7 and legacy PKCS12 exports carry the actual high-bit vendor selector and their resulting certificate/key format identity.

#### Observed PKCS#12 Password Link interoperability discrepancy

OASIS KMIP v2.1 §4.31, Tables 90–92, defines the `PKCS12PasswordLink` Link as a reference to a case-owned `SecretData` object. The typed fixture therefore registers the password as `SecretData`, uses its returned Unique Identifier in the Link, and selects the same object identifier in the typed wrapping specification; the password bytes are never logged. This follows the standard Link model and does not substitute the password text for an object identifier.

The pinned Cosmian 5.28.0 implementation diverges: `crate/server/src/core/operations/import.rs::process_pkcs12` converts the linked identifier to text and uses that text as the PFX password rather than resolving the linked `SecretData` value. Its `crate/server/src/core/operations/export_get.rs` path also obtains the outgoing PKCS#12 password from the `KeyWrappingSpecification` Encryption Key Information identifier. With the standards-shaped SecretData UID link, all 16 password-protected Get/Export PFX rows received `Operation Not Supported` during the prerequisite PFX Import setup; their target Get/Export requests were not sent. These are setup rejections and do not establish support or rejection for the target Get/Export operations. No literal-password workaround is used in the matrix because it would violate the approved standard-shaped case. The observed case-level outcomes are recorded in `tests/integration/cosmian/capability-matrix.json` and the Task 5 report.

The unprotected-password branch completed all 16 typed PFX Get/Export cases. When a Certificate is the requested source and the selected format is PKCS#12 (standard `0x16` or Cosmian's legacy selector `0x88800001`), Cosmian returns the packaged object as a KMIP `PrivateKey`; the response postcondition now follows that typed object identity. Cosmian normalizes legacy PKCS#12 response Key Format Type to standard `0x16`.

DSA needs operation-specific treatment: `openssl/public_key.rs::kmip_public_key_to_openssl` supports TransparentDSAPublicKey input (lines 168 onward), while `export_get.rs::process_public_key` omits the transparent DSA output/default. Private transparent DSA is retained without conversion; PKCS#8 source paths are separate. This refines the earlier handoff's broader DSA ambiguity without inferring DSA signing or pair-generation support.

Cosmian's `crate/kmip/src/kmip_2_1/kmip_types.rs::CryptographicAlgorithm` uses reserved native values: MLKEM_512/768/1024 = `0x39`/`0x3A`/`0x3B`; MLDSA_44/65/87 = `0x3C`/`0x3D`/`0x3E`; SLHDSA_SHA2_128s/128f/192s/192f/256s/256f = `0x3F`–`0x44`; SLHDSA_SHAKE_128s/128f/192s/192f/256s/256f = `0x45`–`0x4A`. These are **reserved in KMIP 2.1**, not vendor-extension allocations. Requests requiring those enum values are excluded from valid 2.1 wire cases (§11; §11.12/Table 443), despite the documented/source provider capabilities. No invented high-bit replacements are assigned.

This also affects ConfigurableKEM generation: `crypto/kem.rs` selects post-quantum components from the same reserved CryptographicAlgorithm fields. Classical-only P256/Curve25519 configurations are valid high-bit root-algorithm cases. Post-only/hybrid configuration fields that would send native MLKEM values are excluded from generation. No invalid generation request is used as setup.

Opaque vendor key fixtures can contain internal KEM tags without those TTLV enums. Direct unwrapped Import/Register retains the generic OpenSSL converter gap. There are 24 wrapped Import/Register probes for the six post-only/hybrid configurations and two key roles; the 36 dependent Get/Export/Encrypt/Decrypt rows are discrepancy probes using that alternative setup. All 24 Import/Register rows were included in the live matrix: 12 Import and 12 Register targets were not sent because prerequisite Cosmian Create Key Pair returned `Operation Not Supported`. ### Inventory parameters, outcomes and finite domains

The inventory enumerates finite algorithm/format/curve/mode branches and meaningful intersections, not every possible integer, plaintext or certificate. Accepted API integer ranges are not closed algorithm lists. Length, data, salt, label, nonce and policy continua use explicit equivalence/boundary representatives: RSA advertised 2048/3072/4096; valid AES mode-specific sizes (XTS total 256/512); HMAC generation 8/256/8192-bit boundaries; GCM every source tag size 12–16 bytes plus 96/128-bit nonce representatives; HKDF salt/info absent/present; PBKDF2 explicit 1/600000 iterations; XOR 2/3/255; RNG 0/1/32/65536 bytes; empty/nonempty data/AAD/tweak; both wrapping encodings. Arbitrary payloads, names, time values and callback/provider state are equivalence classes, not invented finite exhaustive Cartesian products.

RNG Parameters is defined as a structure in §7.36/Table 388, but it is not part of either operation's request payload: RNG Retrieve §6.1.49/Table 316 lists Data Length, and RNG Seed §6.1.50/Table 319 lists Data. The six matrix variants that add `RNG Parameters { RNG Algorithm: Unspecified }` are therefore standards-invalid exclusions, not typed API gaps or server probes. They are marked non-executable with no request sent; the six length-only cases remain the executable live set. This distinction follows the operation payload tables and does not expand KMIPKit's API scope.

The vendor PBKDF2 default of 600000 iterations is documented/source behavior, but **omitting Iteration Count is excluded** from valid wire cases: §7.12/Table 364 makes it mandatory for PBKDF2, together with Salt. With a SecretData source, no redundant DerivationData is sent; with a SymmetricKey source, explicit disposable DerivationData satisfies the same table and the source's use of base bytes/ignored derivation_data is retained as a semantics probe. HKDF's method-specific paragraph makes info optional. The asymmetric case carries an explicitly present empty DerivationData rather than silently omitting the general required field. These rules refine vendor defaults without weakening the standard.

FPE includes all twelve named source presets plus a custom alphabet, text/integer/float and empty/nonempty tweaks. ChaCha20's source nonce is 8 bytes/64 bits, distinct from ChaCha20Poly1305's 12 bytes/96 bits. IV Length is bits and Tag Length bytes (§4.16/Tables 59–60). SHA3 prehashed RSA cases retain the source's digest-size inference discrepancy. Hash/MAC/classical-sign indicator/correlation paths require comparison with the intended full-message result, not merely parsed output. Certify issuer digest remains builder-selected SHA256 for RSA/EC and absent for EdDSA.

Wrapping rows use only compatible targets and lengths: 32-byte AES/SecretData, or small Ed25519 key material so direct RSA OAEP/v1.5 capacity is respected. NoEncoding has no wrapped attributes and byte-string material; TTLVEncoding wraps the typed KeyValue structure. The 44-byte SPKI target is excluded from AES-KW/NoEncoding because it is not a multiple of eight. Asymmetric explicit-format wrapping requests remain valid documented probes where source rejects that combination. Certificate KEK identifiers have separate owned links. The broad documented wrapping promise for XTS/GCM-SIV/ChaCha/FPE is represented by scheme-routing probes; source fallback to KWP must not be called successful execution of the requested scheme.

Expected classifications are plans: 5,675 `typed_success`, 372 `documented_but_source_gap`, 367 `source_documentation_discrepancy`, one Query `known_response_shape_failure`, two `unsupported_probe`, and twelve non-executable `standards_invalid_exclusion` records (six unsigned-CSR exclusions and six invalid RNG-Parameters variants). None is an observation. A server rejection, unsupported result, malformed response or failed cryptographic comparison is failed interoperability even if a finding assertion passes. Only a successful typed response with required fields and correct matching cryptographic semantics may become observed `typed_success`.

Executable test families are explicitly `planned_for_tasks_4_6`; the six normative exclusions instead link to the offline inventory test. Task 7 must establish executable-case parity; the source inventory validator does not claim that future family functions exist. This Green change authorizes no production changes and sends no request. The many independently owned cases will require substantially more live setup than the historical twenty tests: RSA generation, PBKDF2 and 255-share boundaries are expensive, and non-FIPS/provider fixtures can block individual rows. No runtime estimate is asserted before measurement. Serial family selection, durable per-case outcomes and teardown are required when later tasks execute them.

### Hash multipart live re-evaluation

The multipart follow-up is classified against OASIS KMIP v2.1 §6.1, §6.1.24 Tables 235–237, and
§7.8. Section 6.1 defines the multipart sequence and §7.8 requires the server-generated Correlation
Value from the first response on subsequent requests. Hash Table 235 marks request Data as required
for single-part Hash and not required for multipart Hash, while the general §6.1 text says Data is
always required except when Init or Final Indicator is true. KMIPKIT-0021 governs Hash, MAC, and
Sign and takes operation-table field requiredness directly; KMIPKIT-0019's positional Data matrix
is scoped to Encrypt and Decrypt. The integration amendment therefore records the intermediate
Hash omission as an unresolved source interpretation and makes no conformance claim for it. The
revised KMIPKit test sends a, b, and c in three parts as explicit inputs, reuses the first response's
Correlation Value on both later requests, and checks the final result against an independent SHA
known-answer vector. The typed response parser accepts optional multipart output Data, while
single-part required output remains enforced. The live test does not exercise the disputed
intermediate omission.

Against pinned Cosmian 5.28.0, all seven multipart algorithms returned typed Success but the final digest mismatched the vector for `abc`. Inspection of the pinned `crate/server/src/core/operations/hash.rs` shows that the request Correlation Value is supplied as additional input to a fresh digest, while the intermediate response does not return updated Correlation Value. This matches the observed mismatch and points to Cosmian's multipart state handling; it is not a KMIPKit response parser failure. The three SHA-224 single-part requests were rejected as Operation Not Supported; the versioned algorithm documentation advertises SHA-224, but the pinned Hash implementation omits it. All ten outcomes remain non-interoperable, and Hash remains 14/24.
