## Initial operation choice

Discover Versions is the smallest typed request/response candidate because it does not require a managed object identifier, cryptographic payload, or secret result. It is a public explicit operation, not a hidden handshake. Its use does not establish support for other operations, and the fake transport is sufficient to test request-to-response mechanics before a live server exists. The first request advertises only KMIP 2.1 in accordance with the 1.0 product boundary.

Query has a broader required payload (one or more Query Functions); Get requires a Unique Identifier and may return managed-object/key material. Those are poor first requests for isolating the execute boundary.

## Historical independent boundary review snapshot — 2026-10-05

The findings below are retained to explain the design decisions that followed.
Their previous “open” recommendations are superseded by ADR-0013, ADR-0014,
and the current artifact review gate.

An independent read-only agent review on 2026-10-05 confirmed that OD-002, OD-003, and OD-005 are design gates, not implementation details already settled by this draft. The review made no edits and did not approve any option.

- **OD-002 — extension registry and outgoing extension surface:** `docs/architecture/extensions.md` and accepted ADR-0007 promise generic extension creation/sending and immutable per-client registrations with structural/semantic validation. KMIPKIT-0006 assigns extension criticality/recognition to 0007. This draft proposes no registry and no outbound extension constructor, while ADR-0012 bars arbitrary generic `Item` input to `Client::execute`. Candidate paths for the architecture owner are (a) specify a data-only per-client registry and a typed, validated outbound extension representation, including how an extension within a vendor namespace is identified, or (b) revise the owning architecture/ADR and assign registry and outbound extension support to a separately scoped 1.0 feature. Merely registering a Vendor Identification must not cause content the client cannot validate to be treated as understood. Keep OD-002 open until the owner chooses and the 0007/architecture text agree.
- **OD-003 — client/transport crate boundary:** ADR-0003 declares `kmipkit-client` and `kmipkit-transport` public reusable crates. The current manifests have no `publish = false`, and the client depends on the transport crate. A cross-crate `pub Transport::exchange(&[u8], ...)` is technically public from `kmipkit-transport` even when absent from the `kmipkit` facade or marked `doc(hidden)`; that is not an inaccessible raw-send surface. Candidate paths are to accept and document a public low-level exchange API with its compatibility consequences, or to co-locate the exchange and approved adapter boundary behind client-private visibility, which requires reconciling ADR-0003's layer ownership. Keep OD-003 open pending the architecture owner's choice and an API visibility review.
- **OD-005 — execute-only writer audit:** an AST audit is implementable as a static regression control, but Rust privacy alone cannot guarantee one callsite. A proposed check should pin its parser, scan all production client sources, require exactly one permit mint and writer call inside `Client::execute`, reject aliases/re-exports and uninspected macros/includes/conditional paths, fail closed on syntax it cannot analyze, and include adversarial fixtures for those bypasses. CI enforcement and independent human review are separate controls; the audit is not a language-level proof. T008 already scopes this control. Keep OD-005 open until the executable audit contract and failure behavior are approved.

## Normative/source conflicts retained

- `KMIPKIT-DISC-001`, OASIS §11.5: do not infer Continue/Undo execution and rollback effects.
- **OD-001 source evidence (disposition recorded 2026-10-06):** In the pinned HTML, §9.6 around line 43770 states that the option SHALL have one of three values (Undo, Stop, Continue); Table 435 around line 46581 lists those assigned values plus the `8XXXXXXX` Extensions range. The catalog records the three-value SHALL as `KMIPKIT-REQ-SPEC-9.6-001-002` and separately records `KMIPKIT-ELEM-ENUM-VALUE-BATCH-ERROR-CONTINUATION-OPTION-EXTENSIONS-8XXXXXXX` under §11.5. `KMIPKIT-DISC-001` is a separate open §11.5 discrepancy about Continue/Undo execution effects. The delegated project policy `KMIPKIT-DEC-002` accepts assigned outbound values in this slice and preserves every raw decoded Enumeration. It does not claim that Table 435's extension allocation is invalid under OASIS; see `KMIPKIT-DISC-043` and the current 2026-10-06 refresh above.
- `KMIPKIT-DISC-022`, OASIS §9.16: ADR-0002 product scope requires exact 2.1 even though §9.16 states same-major backward compatibility.
- Unknown extension-range Asynchronous Indicator values have no known async permission semantics absent a registered definition. Preserve/validate their wire range but do not treat them as permission for Pending.
- OASIS §9.8 defines Batch Order Option as a server execution-order constraint. Client response association remains ID-based regardless of response ordering; no response order guarantee is inferred from this option.
- Since KMIPKit 1.0 advertises only `(2,1)` in Discover Versions, a successful response's version list is limited to the empty list or the intersection `{(2,1)}`. A non-offered version violates §6.1.16 server response semantics and is rejected.
- Local inventory records no linked OASIS Test Case IDs for the listed client execution requirements; derived tests cite source clauses/tables and are not represented as official OASIS vectors.
