# Feature Specification: KMIP 2.1 Typed Client Execution

**Feature Branch**: `feature/KMIPKIT-0007-spec-corrections`
**Created**: 2026-10-05
**Status**: Draft — delegated maintainer authorization is recorded in `approval-record.md`; the corrected specification PR and its independent review must be complete before implementation.
**Input**: KMIPKit roadmap: establish the synchronous request/response execution path, response validation, delivery reporting, and first typed client operation.

## Scope and normative sources

This feature defines a synchronous Rust execution foundation for an explicitly constructed KMIP 2.1 client request. Its only operation-specific request and response are Discover Versions (OASIS KMIP Specification v2.1 §6.1.16, Tables 211–213). It also defines the bounded low-level transport contract and deterministic fake for this path. The high-level client accepts only a closed set of protocol-typed requests; generic TTLV values remain available for inspection but cannot be submitted through `Client::execute`. The separately documented `kmipkit-transport` API is an explicit caller-owned raw-byte exchange exception under ADR-0014, without KMIP validation or the typed client's zeroizing request owner. This feature does not provide a production constructor, so an application cannot instantiate a usable network client from this feature alone. A separately approved TLS/HTTPS feature in `kmipkit-client` owns construction from validated transport configuration and MUST NOT expose arbitrary transport injection.

The codec and generic message/batch model are dependencies, not reimplemented here. No live TLS/HTTPS backend, C ABI, Java/Python binding, other operation schema, async runtime, or server is introduced. The fake transport makes the request path independently executable until the separately specified TLS/HTTPS vertical transport is available.

## Proposed public Rust contract

The first typed operation variant is `ClientRequest::DiscoverVersions(DiscoverVersionsRequest)`. The client accepts batches only through typed protocol request variants; no generic TTLV item, pre-encoded body, or caller-defined conversion trait is accepted by `Client::execute`. The proposed method signature is `Client::execute(&mut self, batch: ClientBatch, limits: &CodecLimits) -> Result<ClientBatchResponse, ClientError>`. `ClientBatch` carries typed items, item IDs, and validated common message options; the 0007 API does not expose peer-visible Maximum Response Size for Discover Versions. `CodecLimits` controls only local encode/decode resource bounds and is never conflated with that peer field. `Client::execute` performs exactly one exchange. The low-level `kmipkit-transport::Transport::exchange` is public under ADR-0014, accepts caller-owned bytes without client validation or request-owner guarantees, is not re-exported by the facade, and cannot be injected into `Client`. External transport implementers construct responses with public `TransportResponse::new(Vec<u8>)`, which moves bytes into zeroizing-owned storage; `as_bytes(&self)` provides a borrowed view and `Debug` is redacted. This feature has no production constructor; a later TLS/HTTPS feature in `kmipkit-client` owns construction from validated configuration. The executable user-guide example belongs with that constructor; no ignored code example in this draft is claimed to compile.

## Clarification Record

The current approved architecture and local normative text resolve the following without new product decisions:

- Discover Versions is an explicit operation, not a hidden preflight. The first typed request advertises only `[2, 1]`, matching the KMIP 2.1-only 1.0 boundary in ADR-0002.
- The optional request Time Stamp is a caller-supplied Date-Time preserved exactly when present and omitted when absent. This slice does not generate one. Countdown-derived outgoing Time Stamp generation is outside this feature's scope; a future feature proposing it must define its source policy and normative basis under OD-004. Outgoing client-initiated requests never expose or emit Server Correlation Value. Client Correlation Value, if supplied, is not used for per-item matching.
- `Client::execute` accepts only concrete request types through a closed public request enum. The first enum variant is Discover Versions. Future operation specifications may add typed variants before 1.0; callers cannot provide generic `Item`, raw body bytes, or custom conversion implementations. The separately documented low-level `kmipkit-transport::Transport::exchange` is an explicit caller-owned byte-exchange exception under ADR-0014, outside this typed validation and zeroizing-owner guarantee.
- `kmipkit-transport` owns the documented public low-level exchange interface and delivery state under ADR-0014; this feature defines its bounded synchronous contract and fake transport, not a socket/TLS implementation. The client does not accept caller-implemented transports.
- Response item matching uses IDs for multi-item requests, regardless of response ordering. Batch Order Option constrains server execution order; it does not select the response matching algorithm. A response Operation mismatch, duplicate/missing/unexpected item, or invalid response version is rejected as a protocol error. The exact OASIS echo obligations remain distinguished from stricter project validation.
- Discover Versions responses preserve repeated Protocol Version fields and their order. OASIS KMIP Specification v2.1 §6.1.16, Table 212 marks that response field “No, MAY be Repeated” and describes a preference-ordered list; it states no uniqueness rule. The client rejects versions outside the offered intersection, but does not classify repeated equal values as an OASIS violation. Treating repeated fields as values to preserve follows from the table; OASIS does not separately prescribe a duplicate-value policy.
- Batch Error Continuation is transmitted and represented, but its execution effects are not interpreted. The source conflict for Continue/Undo stays open under `KMIPKIT-DISC-001`.
- The separate value-range conflict between §9.6's three-value text and Table 435's extension range is recorded as `KMIPKIT-DISC-043`. KMIPKit's project policy accepts assigned values only for outbound requests in this slice and preserves every raw Enumeration when decoding. This resolves the client behavior without claiming that the Table 435 allocation is invalid under OASIS; the source conflict remains available for upstream clarification.
- An unrecognized critical extension is rejected as OASIS requires. This slice has no extension registrations, so it does not claim support for a vendor critical extension. Unknown non-critical extensions are preserved for inspection as KMIPKit project policy; OASIS §9.13 permits processing them as absent.
- The per-client immutable registry remains required by `docs/architecture/extensions.md` and ADR-0007. ADR-0013 assigns it, typed validated extension values, and generated cross-language adapters to KMIPKIT-0012 before the 1.0 API is frozen. KMIPKIT-0007 rejects unrecognized critical extensions and preserves unknown non-critical values; it does not claim support for registered vendor extensions.
- The Discover Versions response is not classified as likely to be large. The client still enforces the configured local response limit. Each later operation specification must classify its response-size needs against the completed operation inventory and §9.12.

## User Scenarios & Testing

### User Story 1 — Execute an explicit typed Discover Versions request (Priority: P1)

KMIPKit's later approved production-construction feature supplies a configured KMIP 2.1 client. A Rust caller explicitly asks that client to discover server-supported versions and receives a typed outcome through the normal request/response path. This 0007 feature alone provides only the internal execution foundation and deterministic fake.

**Why this priority**: This is the smallest operation-specific vertical slice that exercises typed request construction, the private writer, transport ownership, decoding, response validation, and redacted errors without requiring an existing managed object or secret input.

**Independent Test**: A `kmipkit-client` unit test uses the private test-only factory and deterministic fake transport to capture a complete encoded request and return a valid encoded response; assert the typed request/response and that no discovery occurs unless the caller invokes this operation.

**Acceptance Scenarios**:

1. **Given** an explicit Discover Versions call, **When** the request is encoded and exchanged, **Then** it contains a KMIP 2.1 header and the caller-supported version list `[2, 1]` in decreasing preference order.
2. **Given** a Discover Versions request advertising only `(2,1)`, **When** the response lists no versions or one or more `(2,1)` entries, **Then** the response list and its order, including repeated Protocol Version fields, are preserved; any version not offered by the client or any malformed list is rejected. This does not impose uniqueness beyond OASIS KMIP Specification v2.1 §6.1.16, Table 212, which marks the Protocol Version response field as repeatable. The client does not infer support for any other operation.
3. **Given** a server returns `Operation Not Supported`, **When** the response is processed, **Then** the typed KMIP result is returned without retry or hidden fallback.
4. **Given** no explicit call was made, **When** another client operation is later added, **Then** constructing/executing that operation does not trigger Discover Versions implicitly.

### User Story 2 — Correlate and validate a response batch (Priority: P1)

A caller needs each result associated with the request that produced it, including batches returned in a different order and mixed completed/Pending outcomes. For deterministic execution-path tests, 0007 uses repeated Discover Versions items with the fake transport only; this is not an interoperability claim about server support.

**Why this priority**: Response misassociation can present a result as belonging to the wrong operation; asynchronous status must also respect the caller's explicit request option.

**Independent Test**: Send multiple typed Discover Versions items through the fake transport and return reordered, mixed, malformed, and Pending response batches.

**Acceptance Scenarios**:

1. **Given** a multi-item request with distinct IDs and a response in a different order, **When** the response is validated, **Then** outcomes are matched by ID regardless of Batch Order Option. Batch Order Option controls server execution order; it does not constrain response item order or change client correlation.
2. **Given** a response with a missing, duplicate, or unexpected ID, or a mismatched operation, **When** it is validated, **Then** execution fails with a redacted protocol error and correct delivery state.
3. **Given** a response batch contains both completed and Pending results, **When** the request Asynchronous Indicator permits asynchronous outcomes, **Then** both item outcomes are preserved; when it prohibits them, execution returns a protocol error.
4. **Given** a single-item request, **When** the response omits the optional ID, **Then** its sole response is associated with that request; if an ID was supplied, the response must echo it.

### User Story 3 — Bound and safely report one exchange (Priority: P1)

A caller needs request bytes protected through the transport call, an enforced response limit, and accurate evidence about whether a failed request may have reached the server.

**Why this priority**: The execute path carries potentially sensitive protocol material and network failure can leave request delivery uncertain.

**Independent Test**: Exercise the production `Client::execute` callsite through fake short writes, transport success, failures before and after partial write, response-started failures, oversized replies, and owner drop.

**Acceptance Scenarios**:

1. **Given** any execution failure, **When** the caller inspects the error, **Then** it reports NotSent, PossiblySent, or ResponseStarted accurately and contains no request, response, credential, or key bytes.
2. **Given** a transport performs partial writes, **When** exchange returns success or error, **Then** the encoded owner remains alive until that return and initialized secret bytes are zeroized after the owner is dropped.
3. **Given** an encoded response exceeds the configured local byte limit, **When** transport completes, **Then** it is rejected before TTLV parsing and no response-sized allocation or retry occurs.
4. **Given** transport or protocol failure, **When** execution returns, **Then** no automatic retry, failover, or background polling occurs.

### Edge Cases

- An empty response version list, one or more repeated offered `(2,1)` Protocol Version fields in their received order, a non-offered response version, and malformed version pairs. The initial API advertises a fixed singleton list, so it does not expose caller-supplied version-list choices. Repeated fields are preserved because Table 212 marks Protocol Version as repeatable; no uniqueness violation is inferred.
- Empty/oversized/malformed response framing; exact and one-byte-over configured limits; nesting and element limits forwarded unchanged from `CodecLimits`.
- Duplicate, missing, or unknown batch IDs; duplicate IDs in the request; one-item request without an ID; reordered response with Batch Order Option both absent/false and true.
- Unknown assigned Enumeration values, extension-range values, and unassigned values outside an extension range for Asynchronous Indicator and Batch Error Continuation.
- Pending result with omitted/prohibited asynchronous permission, missing Asynchronous Correlation Value, or an unrecognized extension-range indicator whose semantics do not permit the client to infer Pending permission.
- Unknown critical and non-critical Message Extensions; extension payloads and result messages never appear in Debug output or errors.
- Failures before send, after a partial write, while awaiting the first response byte, and after response reception begins; each preserves the most advanced delivery state and never retries.

## Requirements

### Functional Requirements

- **KMIPKIT-0007-FR-001**: The high-level `kmipkit-client::Client::execute` API MUST be synchronous and accept only a closed set of concrete typed KMIP request values. This initial feature includes only typed Discover Versions request items and MUST NOT accept a generic TTLV `Item`/`Structure`, raw message bytes, or caller-implemented serialization/conversion hooks. The separately documented low-level `kmipkit-transport::Transport::exchange` API may exchange caller-supplied bytes and return a zeroizing raw-response wrapper under ADR-0014; it is not re-exported by the top-level facade, performs no KMIP validation or encoding/decoding, and carries no typed-client guarantee.
- **KMIPKIT-0007-FR-002**: The initial typed operation MUST implement Discover Versions request and response fields in OASIS §6.1.16, Tables 211–213. A request MUST advertise the KMIPKit-supported version `(2,1)` in decreasing preference order. Since the caller's offered list contains only `(2,1)`, a successful response payload MUST be empty or contain only `(2,1)`; any other returned version is a server conformance violation and MUST be rejected. The operation MUST be explicit and MUST NOT be called as an implicit preflight.
- **KMIPKIT-0007-FR-003**: The execution layer MUST use KMIPKIT-0005's bounded decoder/private writer and KMIPKIT-0006's message/batch model without creating an alternate codec or message representation. All per-call codec limits MUST flow through unchanged by borrowed reference.
- **KMIPKIT-0007-FR-004**: Every outgoing request and accepted response MUST use Protocol Version 2.1 under ADR-0002. Other major/minor pairs MUST be rejected. The implementation and documentation MUST identify this as the product-scope exception `KMIPKIT-DISC-022`, not as same-major backward compatibility.
- **KMIPKIT-0007-FR-005**: The low-level transport boundary MUST synchronously exchange caller-supplied request bytes and a bounded response without logging or formatting request/response contents. On success it MUST return a `TransportResponse` whose drop zeroizes the initialized byte range in its current owned allocation before release and whose `Debug` output is redacted. On error it MUST zeroize the initialized byte range of each KMIPKit-owned partial or temporary response allocation before release and before returning a payload-free, redacted `TransportError` with delivery state. Spare or uninitialized capacity is outside these guarantees. An earlier allocation released by response-buffer growth, and every prior allocation used for a growing KMIPKit-owned request copy, MUST be zeroized before that allocation is released. Caller-created copies and copies owned by TLS, the operating system, or third-party transport libraries are outside KMIPKit's zeroization guarantee. Each concrete adapter MUST prevent response-buffer reallocation after response bytes have been stored or zeroize each prior/temporary allocation before release; its specification MUST require tests proving the selected allocation-cleanup strategy on success and error paths and document external-library copy limitations. The transport MUST NOT retain request bytes beyond the synchronous exchange and MUST zeroize KMIPKit-owned temporary request copies before release. Each concrete adapter specification MUST require applicable request nonlogging, nonretention, and temporary-copy cleanup tests. The caller owns the input buffer; direct callers also own the returned response wrapper and any copies they explicitly make. This low-level API provides no KMIP validation or typed-client guarantee. The deterministic fake MUST support partial-write behavior and report monotonic `RequestDeliveryState` transitions. No live network backend is in scope.
- **KMIPKIT-0007-FR-006**: The response MUST be validated against the request before being returned: operation matches, item cardinality and identities match, required IDs are echoed, and reordered items are associated by their IDs. Duplicate, missing, or unexpected response items MUST fail closed. Any stricter project validation MUST be identified separately from the exact OASIS SHALLs.
- **KMIPKIT-0007-FR-007**: The client MUST validate outbound Asynchronous Indicator values against Table 432 and §11.3, preserving assigned and extension-range values while rejecting unassigned values outside those ranges. For Batch Error Continuation, the client MUST enforce option presence/cardinality and MUST reject it on a single-item batch. Under project policy `KMIPKIT-DEC-002`, outbound requests in this slice accept only the three assigned values; the generic model continues to preserve all raw Enumeration values. This decision does not claim that Table 435's extension allocation is invalid under OASIS. The client MUST NOT infer Continue/Undo execution or rollback effects while `KMIPKIT-DISC-001` is unresolved.
- **KMIPKIT-0007-FR-008**: The client MUST represent completed and Pending item results. It MUST accept Pending only when the request's effective Asynchronous Indicator permits it. A Pending result missing the required Asynchronous Correlation Value defined by the accepted KMIPKIT-0006 model MUST be rejected; when present, its opaque bytes MUST be preserved exactly through the `Client::execute` result for later explicit operations. An extension-range indicator MUST NOT be assumed to permit Pending without registered semantics. Poll, Cancel, Process, and automatic waiting remain out of scope.
- **KMIPKIT-0007-FR-009**: The client MUST enforce the configured response-byte ceiling before decoding, and MUST pass the same configured `CodecLimits` reference to encoding and decoding without cloning or reconstructing it. It MUST preserve the difference between the peer-visible Maximum Response Size field and the local decoder/transport limits. Under KMIPKit policy, Discover Versions MUST omit the peer-visible field because this operation is not classified as likely-large. Every later operation spec MUST assess OASIS §9.12's large-response recommendation and define/test peer-size behavior where appropriate.
- **KMIPKIT-0007-FR-010**: An unrecognized critical Message Extension MUST reject the whole message as required by OASIS §9.13. Unknown non-critical extension data MUST be preserved under KMIPKit project policy (`AGENTS.md` §9; OASIS permits processing it as absent). This initial feature registers no recognized critical extensions and MUST NOT claim vendor critical-extension support.
- **KMIPKIT-0007-FR-011**: The request's private encoded owner MUST remain alive for the full synchronous transport exchange and be zeroized after drop. The production writer MUST be private to the client execution module, callable only by `Client::execute`, and require a private `OperationEncodingPermit` whose constructor and only mint site are in the same execute-owning module. There MUST be exactly one production permit mint site and writer callsite.
- **KMIPKIT-0007-FR-012**: `Client::execute` MUST use a closed typed request surface and MUST expose no public generic encoder or caller-selected raw TTLV body. This does not prohibit the separately documented low-level transport byte-exchange API under ADR-0014. The candidate production callsite and its owner-through-transport integration test MUST be in the same change. CI MUST pass the test before merge, enablement, or release, as required by ADR-0012 and KMIPKIT-0005 FR-013.
- **KMIPKIT-0007-FR-013**: Failures MUST preserve accurate delivery state and safe, sanitized cause categories. They MUST NOT retain or display arbitrary original source text, which may contain untrusted or sensitive data. Before an error is returned, each KMIPKit-owned partial response allocation MUST have its initialized byte range zeroized; FR-005 defines the limits for spare capacity, prior allocations, and external copies. Neither error storage nor formatting may expose response contents. Execution MUST NOT automatically retry, fail over, poll, or resubmit. Formatting, logging, and errors MUST redact request/response bytes and all secret material.
- **KMIPKIT-0007-FR-014**: Each normative requirement and project invariant MUST have a stable identifier linked to its exact OASIS/catalog source or policy, implementation location, and executable test before implementation completion. Derived tests MUST NOT be labeled official OASIS test vectors.
- **KMIPKIT-0007-FR-015**: The client MUST preserve an optional caller-supplied request Time Stamp as Date-Time exactly and MUST omit it when absent. This feature MUST NOT synthesize a request Time Stamp from a countdown timer. Countdown-derived outgoing Time Stamp generation is outside this feature's scope under OD-004; a future feature that proposes it must define its time-source policy and normative basis. This feature does not claim that OASIS §9.20 authorizes converting a countdown timer into the outgoing field. Deterministic tests MUST cover exact preservation and omission. The supplied value MUST NOT appear in supported diagnostics, error formatting or exposed error-source chains, and MUST NOT be logged.
- **KMIPKIT-0007-FR-016**: A client-initiated request MUST NOT expose a setter for or emit Server Correlation Value. An optional Client Correlation Value MUST remain distinct from Unique Batch Item ID and MUST NOT be used as the response batch-item match key.
- **KMIPKIT-0007-FR-017**: The Asynchronous Correlation Value MUST be treated as capability-like sensitive metadata: preserve its exact bytes for explicit later operations, expose them only through an explicit borrowed accessor, redact them from `Debug`, `Display`, errors, and logs, and retain KMIPKit-owned copies in zeroizing storage until drop. The implementation MUST NOT create an ordinary unzeroized duplicate.

### Key Entities

- **Typed Client Request**: Closed protocol request variant; initially Discover Versions only.
- **Client Batch**: One or more typed request items plus validated common batch options and correlation IDs.
- **Discover Versions Payload**: Caller-supported KMIP versions and server-supported response versions, preserving list order.
- **Pending Result**: A typed result permitted by request options and carrying the required opaque Asynchronous Correlation Value unchanged for later explicit operations.
- **Transport Exchange**: One synchronous write/read interaction with delivery evidence and bounded response bytes.
- **Operation Encoding Permit**: Private capability minted only during `Client::execute` to authorize the sole production writer call.
- **Codec Limits**: The unchanged caller-selected TTLV message, nesting, and element-count limits.

## Success Criteria

### Measurable Outcomes

- **KMIPKIT-0007-SC-001**: Every outgoing request and accepted response header is KMIP 2.1; acceptance passes an iff-property over signed 32-bit major/minor values.
- **KMIPKIT-0007-SC-002**: The deterministic fake demonstrates valid explicit Discover Versions success, empty version list, KMIP error result, reordered correlated batch, mixed Pending/completed results, exact Asynchronous Correlation Value byte preservation, and rejection of malformed batch identity or Pending results missing that value.
- **KMIPKIT-0007-SC-003**: The compliant fake stops retaining response bytes at the configured cap; the client rejects an oversized `TransportResponse` returned by a deliberately non-compliant fake before decoder invocation; successful wrapper drop and partial-read error cleanup zeroize every initialized byte in the current KMIPKit-owned response allocation; the peer Maximum Response Size field is absent for Discover Versions; and the exact same borrowed `CodecLimits` reference reaches encoder and decoder. These fake tests do not claim that spare/uninitialized capacity, previous allocations, or external-library copies are cleared and are not evidence about production adapter allocation behavior. Each adapter specification must define and test its response-buffer growth strategy and cleanup on success and errors.
- **KMIPKIT-0007-SC-004**: Production source audit finds exactly one permit mint and one private writer callsite, both in the `Client::execute` path; no other `kmipkit-client` path can submit generic TTLV. The separate public transport byte-exchange exception is documented under ADR-0014.
- **KMIPKIT-0007-SC-005**: Fake transport tests prove delivery state for pre-send, partial-write, and response-started failures, no retry, request-owner lifetime through exchange return, zeroization after drop, and redaction in `Debug`, `Display`, and any exposed typed error-source chain.
- **KMIPKIT-0007-SC-006**: Changed client/protocol/transport lines meet at least 95% line coverage and every in-scope normative or policy requirement has an implementation and executable-test link before implementation PR review.
- **KMIPKIT-0007-SC-007**: A caller-supplied request Time Stamp is preserved exactly, an absent value remains absent, and no Time Stamp is synthesized; the supplied value is absent from supported diagnostics, error formatting and exposed error-source chains, and any logging on the execution path; no Server Correlation Value is emitted.
- **KMIPKIT-0007-SC-008**: A Pending Asynchronous Correlation Value survives unchanged while its result is live and is available only through its explicit borrowed accessor; a sentinel is absent from `Debug`, `Display`, errors, and captured logs, and KMIPKit-owned storage is zeroized when dropped without an ordinary unzeroized duplicate.
- **KMIPKIT-0007-SC-009**: Direct low-level fake exchanges carrying a unique request sentinel prove that it is absent from captured logs and from fake-retained state after both success and error. A test-only observer confirms that every initialized byte in any KMIPKit-owned temporary request copy is zero before deallocation. This verifies the fake contract only; each concrete adapter specification must assign applicable request nonlogging, nonretention, and temporary-copy cleanup tests and document external-library copies.

## Design dispositions and remaining release gate

- **KMIPKIT-0007-OD-001 — Batch Error Continuation extension range (implementation disposition recorded)**: The pinned OASIS §9.6 and Table 435 conflict is cataloged separately as `KMIPKIT-DISC-043`; it is not `KMIPKIT-DISC-001`, which concerns §11.5 Continue/Undo execution effects. The delegated project decision `KMIPKIT-DEC-002` accepts only assigned values for outbound Batch Error Continuation in this client slice while generic decoding preserves all raw values. This is a conservative KMIPKit policy, not an assertion that OASIS invalidates the extension allocation. A future extension registry or upstream clarification may propose a separately reviewed change.
- **KMIPKIT-0007-OD-002 — Extension registry scope and ownership (resolved by ADR-0013)**: KMIPKIT-0007 owns common criticality behavior: reject unrecognized critical extensions and preserve unknown non-critical data. KMIPKIT-0012 owns the immutable per-client registry, validated typed extension values, and generated Rust/C/Java/Python adapters before the 1.0 API is frozen. This split keeps ADR-0007's 1.0 commitment and does not claim vendor extension support before KMIPKIT-0012.
- **KMIPKIT-0007-OD-003 — Client/transport visibility and cap ownership (resolved by ADR-0014)**: `kmipkit-transport::Transport::exchange` is a documented public low-level API because ADR-0003 declares the crate public and reusable. It intentionally accepts caller-owned request bytes and returns a `TransportResponse` wrapper, without KMIP validation or typed-client guarantees; wrapper/drop and partial-error cleanup zeroize initialized bytes in each current KMIPKit-owned allocation. Spare capacity, prior allocations not cleared before reallocation, caller copies, and external TLS/transport-library copies are outside that guarantee. Every concrete adapter must prevent response-buffer reallocation after bytes are stored or clear every prior/temporary allocation before release, with success/error tests proving that behavior; request nonlogging, nonretention, and applicable temporary-copy cleanup tests are also required. The exact limits are defined by ADR-0014. This is an explicit low-level exception to ADR-0012 Decision 4; `Client::execute` always decodes the wrapper and never exposes raw bodies. The API is not re-exported by the facade, and no public client constructor accepts a caller-implemented transport. `Client::execute` passes exactly `limits.max_message_bytes()` and independently checks response length before decoding. This feature verifies the fake contract; no concrete network adapter exists in this scope.
- **KMIPKIT-0007-OD-004 — Countdown-derived outgoing Time Stamp excluded from this feature**: Pinned OASIS KMIP Specification v2.1 §9.20 makes the request Time Stamp optional and Table 425 encodes it as Date-Time. Section 9.20 notes that a server may reject a client Time Stamp that is too far from its own time. Its countdown-timer note describes deriving “seconds from now” values from Date attributes by subtraction; it does not explicitly authorize serializing a monotonic countdown as the outgoing Time Stamp. This feature therefore preserves a caller-supplied Date-Time exactly or omits the field, with no generated time source. Countdown-derived outgoing Time Stamp generation is out of scope for 0007 and is not an implementation gate for this feature. A future feature proposing it must define the time-source policy and normative basis; this disposition does not claim that §9.20 authorizes that behavior.
- **KMIPKIT-0007-OD-005 — Auditable execute-only writer callsite (resolved by this contract)**: A pinned Rust-AST audit scans all production `kmipkit-client` sources, requires exactly one private permit mint and one writer call inside `Client::execute`, rejects aliases/re-exports and hidden or generated source paths, inspects macro token trees for the protected identifiers, and fails closed on source constructs it cannot inspect. Adversarial fixtures cover aliasing, macro-token, re-export, include, and conditional-compilation bypasses. CI runs the audit; it is a regression control, not a language-level proof, and independent security review remains required.
- **KMIPKIT-0007-OD-006 — Secret-bearing request test ownership (resolved as a later mandatory gate)**: KMIPKIT-0007 introduces the sole callsite and its owner-through-transport test using non-secret Discover Versions data. The first later operation specification whose typed request can contain secret-bearing TTLV must add an operation-specific lifecycle test through the existing `Client::execute`, covering partial writes, success/error return, owner lifetime, zeroization, redaction, delivery state, and no retry. That specification must resolve this gate before approval or enabling the operation; no secret-bearing request may be sent before its candidate test passes CI.

## Assumptions and exclusions

- KMIPKIT-0005 and KMIPKIT-0006 contracts are accepted and merged before implementation. This draft cannot approve or supersede them.
- Rust is the only API in this slice. C ABI and language bindings are later parity work.
- The synchronous transport trait and fake are included; this feature is an internal execution foundation and has no production constructor. TLS/HTTPS production backends and a supported constructor from validated TLS/HTTPS configuration are supplied by a separately approved transport feature/specification; that feature must not expose arbitrary transport injection.
- Discover Versions is not guaranteed to be supported by all servers and does not establish support for any other operation.
- This feature does not send secret-bearing payloads or implement cryptographic algorithms, credentials, TLS configuration, server-initiated operations, retry/failover, background polling, or cryptographic-material persistence. It does not authorize a later secret-bearing request path.
- Generic TTLV remains a public inspection/extension value model but cannot be submitted through `Client::execute` to bypass its typed boundary. The separate low-level transport caller-byte exception is defined by ADR-0014.
