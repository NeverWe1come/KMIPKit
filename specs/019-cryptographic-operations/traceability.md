## Cryptographic Parameters structure-member validation

OASIS KMIP v2.1 §4.16 describes Cryptographic Parameters as a “set of OPTIONAL fields”; Table 59 identifies each named member and its TTLV encoding, and Table 487 supplies the allocated tags. §4.16 does not state a separate maximum-occurrence sentence for these members. The accepted T020/T021 task criteria require known Cryptographic Parameters child type/cardinality validation; the feature-level interpretation tested here treats each named Table 59 member as a singleton for cardinality checking. This is an accepted feature criterion, not a claim that §4.16 states an explicit per-member `MUST` against repetition. Each malformed case supplies only the selected member(s), so optional or conditional presence requirements do not independently cause rejection. Encrypt and Decrypt validation each reject duplicate and wrong-Item-Type cases for all 18 Table 59 members. Unknown members remain accepted and preserved in original order by both request conversions, as covered by `encrypt_tests::request_preserves_supplied_cryptographic_parameters_members_and_order`, `decrypt_tests::request_preserves_supplied_cryptographic_parameters_members_and_order`, and `cryptographic_parameters_tests::unknown_parameter_members_survive_in_original_order_and_encoding`. Exact T020 and T021 evidence is in the corresponding `.superpowers/sdd/kmipkit-0019-cryptographic-operations/task-20-report.md` and `task-21-report.md`.
