# ADR-0012: Conditional Caller-Requested TTLV Wire Encoding

**Status**: Accepted — maintainer authorization delegated to Codex on 2026-10-05; see `specs/005-ttlv-wire-codec/approval-record.md`.
**Date**: 2026-10-05
**Decision owner**: KMIPKit maintainer
**Related specification**: [KMIPKIT-0005 TTLV Wire Codec](../../specs/005-ttlv-wire-codec/spec.md)

## Context

`AGENTS.md` §8 prohibits logging, formatting, serializing, or including credentials, private keys, secret key material, OTPs, tickets, and raw KMIP bodies in errors. KMIPKIT-0005 implements a private outbound TTLV writer that may carry such values, but has no production callsite. ADR-0011 concerns the disposition of received Reserved Tags and does not authorize wire encoding.

The `AGENTS.md` §8 baseline remains in force for diagnostics, general-purpose serialization, persistence, and the release branch production path. This accepted ADR authorizes KMIPKIT-0005 only to implement and unit-test the private, uncalled writer/owner described below; it does not authorize a production callsite or secret-bearing send. No OASIS clause creates this project-policy exception.

## Decision

1. The delegated maintainer authorization recorded in `specs/005-ttlv-wire-codec/approval-record.md` accepts this ADR, the KMIPKIT-0005 feature specification, and the enforceable permit/closed-request boundary design. It authorizes KMIPKIT-0005's private, uncalled writer/owner. A later client feature may add a production path for temporary outbound TTLV solely to carry a KMIP operation explicitly requested by the caller. That candidate client feature PR must include both the sole production callsite and its owner-through-transport integration test. CI must run and pass the test against that candidate callsite before the PR is merged, enabled, or released. Until that gate passes, the release branch must contain neither the production callsite nor a secret-bearing send; an unmerged candidate callsite does not authorize sending secret-bearing data.
2. KMIPKit must own the outbound bytes in a zeroizing buffer and retain that owner through the transport write. Before deallocation/owner drop, KMIPKit must zeroize the initialized encoded byte range. Spare or otherwise uninitialized `Vec` capacity is outside this guarantee unless it is explicitly initialized and its cleanup is verified. Caller, TLS-library, and runtime copies are also outside KMIPKit's guarantee.
3. This decision does not permit diagnostic or general-purpose serialization, serialization traits, logging, formatting, inclusion in errors, persistence, or unnecessary copies.
4. This decision does not permit arbitrary inbound raw-byte retention or re-emission. Inbound messages must be handled through the decoded model; no opaque raw-body path is authorized by this ADR.
5. The approved architecture keeps the public generic TTLV tree and bounded decoder in `kmipkit-ttlv`. Byte-producing outbound encoding has no public `encode(&Item)` API. KMIPKIT-0005 may implement and unit-test a private `kmipkit-client` writer/owner, but it adds no `Client::execute`, permit type/constructor, or production writer callsite. The first client feature/spec owns the production boundary: an internal `OperationEncodingPermit` whose type and private constructor live in the module that owns `Client::execute`; only `Client::execute` creates the permit and calls the private writer. With the writer in a private child module, its entry point may use `pub(super)` or equivalent visibility restricted to the parent module; do not use `pub(crate)` or export the module, permit, or owner. That client feature must verify exactly one production callsite and permit mint site. Its `Client::execute` accepts only a closed set of concrete, protocol-typed KMIP request variants: no caller-supplied generic `Item`, raw body, or public caller-implementable conversion trait. The first client feature/spec defines the exact request surface and proves that boundary. The dependency direction is acyclic: `kmipkit-client` may depend directly on `kmipkit-ttlv`, while `kmipkit-protocol` already depends on `kmipkit-ttlv`. The KMIPKIT-0005 authorization is limited to its private uncalled writer/owner; a production path remains gated on the first-client candidate integration test passing CI.
6. The first client feature/spec that sends secret-bearing TTLV owns an integration test proving that callers can submit only the closed typed request set, only `Client::execute` can mint and pass the permit, and the zeroizing owner remains alive through every partial transport write until the transport returns success or error. On both transport success and write error, the test must verify owner lifetime/drop and the failure-delivery state required by `AGENTS.md` §8: not sent, possibly sent, or response reception had begun. No automatic retry is permitted. The candidate client feature PR must contain both this test and its sole production callsite; CI must pass the test against that callsite before the PR is merged, enabled, or released. Until then, the release branch must have no production callsite and no secret-bearing send. If review rejects this boundary, or the permit/request boundary cannot be enforced, do not approve or implement a secret-bearing encoder.

## Rationale

A KMIP client needs a wire representation to carry a requested operation, but temporary transport bytes have a different lifecycle from diagnostics, persistent data, or a general serialization format. A future client feature's private permit can make the request path explicit: the module containing `Client::execute` owns the unforgeable-to-callers token, and the execute input cannot be replaced by an arbitrary generic Item or caller-defined conversion. Keeping the codec writer private and uncalled in KMIPKIT-0005 preserves the current prohibition. The first client feature PR may introduce its sole production route together with the test that exercises it; CI must pass that test before the route is merged into the release branch or used to send secret-bearing data. A KMIPKit-owned zeroizing buffer minimizes exposure by clearing the initialized encoded bytes before deallocation, while preserving the redaction and no-persistence rules. Spare/uninitialized capacity is not covered unless explicitly initialized and verified. The public TTLV crate remains useful for generic values and bounded decoding without exposing a general-purpose byte-producing encoder.

## Consequences

- The release branch has no production writer callsite or secret-bearing send until the first-client candidate PR includes the sole callsite and owner-through-transport integration test and CI passes against that candidate.
- This ADR, the specification, and the enforceable boundary are authorized together in `specs/005-ttlv-wire-codec/approval-record.md`.
- The feature specification and implementation contract must preserve the limits above and provide policy/owner verification separate from OASIS conformance tests.
- KMIPKIT-0005 owns codec-level encoding vectors and private encoder owner/policy unit tests in `kmipkit-client`; it adds no `Client::execute`, permit, or production writer callsite and does not claim a request-path or transport integration test.
- The first client feature/spec owns the caller-facing API, permit type/private constructor, sole production mint/callsite, exact-one audit, and request-path integration test. It covers partial writes and transport success/error return, owner lifetime through the return, drop/zeroization of initialized bytes, correct failed-request delivery-state reporting, and absence of automatic retry. Its candidate PR contains both the callsite and test; CI must pass the test against the candidate callsite before merge, enablement, or release. The release branch must contain no callsite or secret-bearing send before that gate passes.
- If the private request-only boundary cannot be enforced, no production secret-bearing request path may be implemented; this does not relax the diagnostic, general-purpose serialization, or persistence prohibitions.

## Alternatives Considered

- **Treat encoding as already exempt from the rule**: Rejected because `AGENTS.md` §8 explicitly includes serialization of raw KMIP bodies and no accepted ADR authorizes an exception.
- **Permit general-purpose serialization of secret-bearing values**: Rejected because it would broaden persistence, copying, logging, and caller-controlled output paths.
- **Retain or replay arbitrary inbound raw bodies**: Rejected because it would bypass model validation and create an uncontrolled secret-retention and re-emission path.

## Implementation Gate

The maintainer delegated execution and approval of the implementation plan without further manual intervention on 2026-10-05. That authorization accepts this ADR, the KMIPKIT-0005 specification, and the enforceable boundary design recorded in `specs/005-ttlv-wire-codec/approval-record.md`. Those approvals permit only the private, uncalled codec writer/owner in KMIPKIT-0005. They do not add a production route. KMIPKIT-0005 must not add `Client::execute`, permit type/constructor, or a production writer callsite. The first client feature/spec owns the exact public typed request/limit API, the execute-owned permit type/private constructor and sole mint site, and the sole production writer callsite with parent-restricted visibility (`pub(super)` or equivalent, never `pub(crate)`). Its implementation must audit exactly one writer callsite and one mint site. The execute API must accept a closed set of concrete typed KMIP requests and expose no generic `Item`, raw-body, or caller-implementable conversion route; its exact surface belongs to that first client feature/spec. The candidate client feature PR must contain both the production callsite and integration test covering partial writes, owner lifetime through transport success/error return and subsequent zeroization of initialized bytes, correct `AGENTS.md` §8 failed-request delivery-state reporting, and no automatic retry. CI must pass the test against the candidate callsite before merge, enablement, or release. The release branch must contain no production callsite or secret-bearing send until that gate passes. If the boundary cannot be enforced, do not implement the exception or any secret-bearing request path. Do not change `AGENTS.md` or treat ADR-0011 as authority for this policy.
