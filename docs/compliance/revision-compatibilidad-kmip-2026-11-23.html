Compatibilidad de KMIPKit con KMIP 2.0, 2.1 y 3.0

Revisión de código y especificaciones · 23 de noviembre de 2026 · release/1.0.0-review · e710308d7bb4

Actualización del árbol de trabajo. La sección de correcciones documenta el cierre de los 16 hallazgos de esta revisión. Ver correcciones y evidencia

KMIPKit sí es una biblioteca cliente. Tiene rutas identificables para todas las operaciones de las tres ediciones, en ambas direcciones. La implementación completa y la promesa de poder programar todo KMIP mediante nombres son falsas en esta revisión. Se pierden datos de solicitudes válidas, se bloquean operaciones permitidas y varios nombres públicos tienen un significado distinto del asignado por OASIS. El diagnóstico resulta del código del propio cliente.

C2S significa solicitud iniciada por el cliente y S2C solicitud iniciada por el servidor. Discover Versions, Query y Set Endpoint Role figuran en ambas direcciones y comparten código. Por eso 57 + 5 en 2.1 corresponden a 59 códigos distintos. Notify y Put son exclusivamente S2C. Las seis incorporaciones de 2.1 y las siete del borrador 3.0 son C2S.

El criterio solicitado incluye los campos opcionales, las variantes y la ergonomía de la API. La definición formal de cliente conforme de OASIS exige satisfacer al menos un perfil de cliente y las cláusulas aplicables de cada perfil declarado. Un fallo en una característica opcional basta para refutar la cobertura universal solicitada. Para atribuirlo a un perfil concreto hay que comprobar sus requisitos. 2.0 §14.1 · 2.1 §14.1 · 3.0 §14.1

Hallazgos que cambian el resultado

1. Un lote 3.0 con dos operaciones no puede superar la ruta tipada

3.0 · C2S · construcción del mensaje

OASIS permite repetir Batch Item y ha retirado Unique Batch Item ID. La validación de ClientBatch exige un ID en cada elemento si hay más de uno, con independencia de la versión. Si el llamador lo omite recibe MissingBatchItemId. Si lo aporta, el constructor lo serializa y la validación 3.0 del mensaje rechaza ese mismo campo. Esto afecta incluso a un lote de dos operaciones independientes.

3.0 §8.1.1 · 3.0 §8.1.3 · execute.rs · L8315 · execute.rs · L8896 · validation.rs · L618

2. Ephemeral tiene una etiqueta y una semántica equivocadas

3.0 · mensaje · entrada y API

El borrador conserva la etiqueta 0x420154 y cambia su tipo a Enumeration. Los valores 1, 2 y 3 seleccionan la omisión de Data, una respuesta vacía o la conservación de Unique Identifier. La validación rechaza explícitamente 0x420154 y reconoce 0x4201BF, asignada a Encrypt Counter. EphemeralMode denomina los valores No, Immediate y RetainOnFailure y los documenta en términos de destrucción del objeto. Una comprobación local confirmó el rechazo del elemento oficial con valor 1.

3.0 §8.1.3 · 3.0 §11.21 · 3.0 §11.58 · validation.rs · L618 · batch.rs · L68 · enums.rs · L823

3. Los métodos asíncronos directos construyen una cabecera 2.x con versión 3.0

3.0 · C2S · Cancel, Poll, Process y Query Asynchronous Requests

Las cuatro funciones execute_* usan build_async_request_message. Aunque recibe la versión seleccionada, siempre añade Batch Count = 1. El propio analizador rechaza Batch Count en una cabecera 3.0. El constructor de lotes general sí omite Batch Count para esa versión. La avería corresponde a la ruta asíncrona directa.

3.0 §8.1.2 · execute.rs · L7843 · execute.rs · L8054 · execute.rs · L9012 · validation.rs · L471

4. La validación 2.0 impide modificar y eliminar Cryptographic Parameters

2.0 · C2S · operaciones de atributos

La tabla 60 de §4.16 autoriza al cliente a modificar y eliminar este atributo. VersionGate lo incluye en su lista de etiquetas prohibidas para mutación. El cliente aplica esa lista, entre otras, a Modify Attribute, Set Attribute y Delete Attribute. Una petición válida sobre un objeto aplicable se detiene antes del transporte. La consulta local al filtro con la etiqueta 0x42002B devolvió prohibición.

2.0 §4.16 · version_gate.rs · L230 · execute.rs · L8432

5. Get Attributes sólo expresa el identificador como texto

2.0, 2.1 y 3.0 · C2S · selección del objeto y lectura

GetAttributesRequest conserva Option<String> y emite Text String. La respuesta exige el mismo tipo mediante copy_text_string. En 2.x esto impide expresar explícitamente, por ejemplo, el índice Integer de un resultado previo en un lote. En 3.0 la solicitud requiere Unique Identifier y §4.68 exige admitir las formas de referencia en su contexto. El modelo común UniqueIdentifier tampoco tiene variantes Reference y NameReference, aunque el modelo TTLV sí las reconoce.

2.0 §4.51 · 2.1 §4.58 · 3.0 §4.68 · 3.0 §6.1.26 · get_attributes.rs · L23 · get_attributes.rs · L264 · create.rs · L75

6. Seis operaciones nuevas de 3.0 pueden rechazar un resultado satisfactorio

3.0 · C2S · interpretación de respuestas

Create Group, Create User, Create Credential y Deactivate delegan el identificador devuelto a parse_success_identifier. Encapsulate y Decapsulate usan otro lector con la misma restricción. Admiten texto, entero y enumeración, pero omiten el tipo Identifier que define el borrador para identificar el objeto creado. En memoria, una respuesta Create Group satisfactoria con un Identifier llegó al modelo de mensaje y falló al convertirla a CreateGroupResponse. Obliterate tiene una respuesta vacía y queda fuera de este hallazgo.

7. Notify pierde las referencias a atributos estándar eliminados

2.0, 2.1 y 3.0 · S2C · datos entregados al callback

OASIS permite una Attribute Reference en forma de Enumeration para una etiqueta estándar y de Structure para un atributo de fabricante. ServerNotifyRequest sólo añade la referencia si su valor es Structure. Con un UID de texto válido en 2.0 y 2.1, una referencia estándar enviada produjo cero referencias en el callback. Además, el lector de UID de Notify sólo acepta Text String, de modo que en 3.0 un Identifier falla antes de que el manejador pueda procesar el evento.

2.0 §6.2.2 · 2.1 §6.2.2 · 3.0 §6.2.2 · 2.1 §5.5 · 3.0 §4.68 · notify.rs · L73 · attribute_reference.rs · L79

8. Put inventa una función ausente y restringe los identificadores

2.0, 2.1 y 3.0 · S2C · validación de entrada

La tabla de mensajes Put marca Put Function como requerido. Si falta o tiene otro tipo, el lector usa NEW como valor predeterminado. Un manejador puede recibir una operación normalizada a New sin que el emisor la haya especificado. Además, Unique Identifier y Replaced Unique Identifier se leen como Text String. En 3.0 eso impide entregar al consumidor un reemplazo con identificadores nativos. La regla que reinterpreta Replace como New cuando el objeto anterior no existe sí tiene una función explícita y es una condición distinta.

2.0 §6.2.3 · 2.1 §6.2.3 · 3.0 §6.2.3 · put.rs · L137 · put.rs · L217

9. Query S2C devuelve Vendor Identification dentro de otra estructura

2.0, 2.1 y 3.0 · S2C · respuesta del cliente

En §6.2.4 Vendor Identification y Server Information son campos hermanos del Response Payload. El primero es obligatorio si se consulta información de servidor. Aun configurando un proveedor, respond introduce Vendor Identification dentro de Server Information. La API de capacidades tampoco dispone de miembros para anunciar, por ejemplo, Attestation Type, RNG Parameters o Profile Information. El switch sólo construye respuestas para operaciones, objetos, información de servidor y las dos consultas de extensiones.

2.0 §6.2.4 · 2.1 §6.2.4 · 3.0 §6.2.4 · query.rs · L29 · query.rs · L155 · query.rs · L244

10. Query confunde la consulta de credenciales con las comprobaciones CRL

2.0, 2.1 y 3.0 · C2S · enumeración y respuesta

El nombre Rust PERFORMS_CRL_CHECKS envía 0x0F. En 3.0 ese valor solicita Credential Information. Performs CRL Checks es una etiqueta independiente. El validador acepta 0x0F incluso en 2.x, donde la tabla termina en 0x0E antes de las extensiones. Además, para cualquier respuesta no vacía el lector exige Protection Storage Masks. En 3.0 la tabla de Query sólo lo exige cuando se solicitó. Así se rechaza una respuesta válida que sólo enumera operaciones. El catálogo generado contiene el nombre correcto para 0x0F, en contradicción con el tipo de la operación.

2.0 §11.43 · 2.1 §11.44 · 3.0 §11.46 · 3.0 §6.1.47 · query.rs · L78 · query.rs · L635 · named_values_generated.rs · L4371

11. OperationCode no coincide con las operaciones que sí envía el cliente

2.x y 3.0 · API por nombres

La enumeración pública omite PKCS#11 (0x33) en las tres ediciones. En 3.0 llama KemEncrypt a 0x3C y KemDecrypt a 0x3D, que pertenecen a Create Group y Obliterate. Carece de los discriminantes 0x3E–0x40. Un consumidor que seleccione por esos dos nombres obtiene códigos de gestión de objetos. Las constantes internas y las factorías dedicadas del ejecutor sí mapean esas operaciones a los códigos OASIS correctos. Esta distinción explica cómo pueden coexistir un inventario completo y una API pública engañosa.

2.1 §11.36 · 3.0 §11.37 · enums.rs · L571 · execute.rs · L245 · pkcs11.rs · L10

12. Hay enumeraciones públicas de objeto y algoritmo sin asignación OASIS

2.x y 3.0 para Object Type · 3.0 para KEM

ObjectTypeCode identifica 0x06 como Template, un valor reservado, y su conversión se detiene en 0x0C aunque 3.0 asigna cuatro tipos de credencial entre 0x0D y 0x10. El modelo ObjectType usado por otras API sí ofrece las credenciales por nombre. KemAlgorithmCode añade ML-KEM-512, 768 y 1024 como 4, 5 y 6: la tabla KEM Algorithm sólo asigna RSASVE, DHKEM y MLKEM antes del espacio de extensiones. Los nombres de los tres tamaños pertenecen a Cryptographic Algorithm y tienen otros números.

3.0 §11.35 · 3.0 §11.26 · 3.0 §11.12 · enums.rs · L682 · enums.rs · L782 · named_values_generated.rs · L4099

13. Los modelos heredados conservan campos y obligatoriedades de 2.1

3.0 · C2S · solicitudes de claves, búsqueda y revocación

Create Key Pair añade Seed en la raíz del payload. El modelo sólo construye los seis grupos de 2.1. Locate sustituye Object Group Member por Object Class Mask, mientras el modelo sigue ofreciendo y emitiendo Object Group Member. Re-key Key Pair exige Unique Identifier y el serializador escribe Private Key Unique Identifier. En Revoke, la tabla hace Revocation Reason opcional pero el constructor lo exige y siempre lo serializa. Elegir V3_0 en las opciones del cliente no selecciona otros serializadores para estas solicitudes.

14. El emisor tipado carece del campo de lote Ephemeral en 2.x

2.0 y 2.1 · C2S · opción estándar

En 2.x el llamador puede solicitar que el servidor omita Data mediante el booleano Ephemeral. El analizador conoce ese campo. En cambio, ClientBatchItem guarda solicitud, identificador del lote y extensiones, y build_request_batch_item sólo emite esas partes. A través de ese constructor el programador no puede pedir esta opción aunque conozca su nombre. Construir el mensaje TTLV a mano cambia el nivel de API y no satisface la ergonomía solicitada.

15. Seed Private Key queda bajo las reglas genéricas de material

3.0 · objetos y formatos

El formato 0x18 tiene un nombre generado, pero el modelo de Key Material sólo asigna tipos hasta 0x17. Para los demás acepta Byte String o Structure y no verifica los miembros internos de ese formato. §3.4 define Structure con Seed o Key. El llamador puede construir la representación correcta a bajo nivel, pero la validación del formato deja pasar representaciones ajenas al esquema.

16. Añadir un nombre a una clave construye un atributo incorrecto en las tres ediciones

2.0, 2.1 y 3.0 · C2S · Create y Create Key Pair

El atajo de nombre para claves simétricas y el utilizado para los atributos del par de claves llaman a name_attribute. En 2.x la estructura Name tiene primero Name Value y después Name Type. El constructor inserta los dos hijos en orden inverso. La regla TTLV exige el orden de la definición. En 3.0 Name pasa a ser un Text String directo; el mismo constructor sigue produciendo la estructura antigua y el filtro recursivo para 3.0 prohíbe sus etiquetas internas. Una aplicación que se limite a usar el método name puede obtener un mensaje mal ordenado en 2.x o un rechazo local en 3.0.

Cambios de esquema que afectan a operaciones compartidas

Para detectar errores de arrastre, comparé por dirección y nombre las tablas de payload presentes en las ediciones, incluidos el orden y los marcadores de obligatoriedad. Las siguientes diferencias de solicitud explican por qué heredar un código de operación de 2.x no basta. Son requisitos de la edición de destino. El detalle sobre qué incumple el código aparece en los hallazgos.

PasoDiferencia observada
2.0 → 2.1Query incorpora Object Groups opcional. Se añaden Set Defaults, Set Constraints, Get Constraints, Query Asynchronous Requests, Process y Ping.
2.1 → 3.0Unique Identifier pasa de opcional a requerido en 25 tablas comparables: Activate, Add Attribute, Adjust Attribute, Archive, Check, Decrypt, Delete Attribute, Destroy, Encrypt, Export, Get, Get Attributes, Get Attribute List, Get Usage Allocation, MAC, MAC Verify, Modify Attribute, Obtain Lease, Recover, Revoke, Re-certify, Re-key, Set Attribute, Sign, Signature Verify. Re-key Key Pair cambia también el nombre del identificador requerido.
2.1 → 3.0Create Key Pair incorpora Seed; Locate cambia el filtro de grupo por la máscara de clase; Query retira Object Groups de la tabla de solicitud y añade la respuesta condicional de credenciales; Revoke pasa a permitir la omisión de Revocation Reason.
2.1 → 3.0Se incorporan Create Credential, Create Group, Create User, Deactivate, Decapsulate, Encapsulate y Obliterate. Las cinco operaciones S2C se mantienen, pero el tipo del identificador y el modelo de mensaje cambian.

Conclusión para la rama evaluada. Se puede describir KMIPKit como cliente multiversión con rutas para todas las operaciones C2S y S2C de KMIP 2.0, 2.1 y 3.0 CSD02, y con API por nombres para numerosos usos. El código contradice una declaración de compatibilidad íntegra con cualquiera de las tres ediciones y una garantía de acceso completo mediante la API de alto nivel.
