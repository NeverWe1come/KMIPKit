# KMIP interoperability server matrix

Status: research and measured integration evidence, not a conformance claim

Research checked: 2026-10-11; Cosmian 5.28.0 source grouping and exhaustive live evidence reconciled on 2026-10-17.

This document keeps two questions separate: what a server publicly declares for each KMIP operation, and what KMIPKit has actually exercised against a server. A declared operation is not an integration-test result. A passing integration test proves interoperability only for the recorded operation, payload, transport, product version, and configuration.

KMIPKit 1.0 targets KMIP 2.1, TTLV, and client-initiated operations, including asynchronous request flows. Set Endpoint Role (§6.1.54) is the explicit exception: its mandatory success transition makes the local endpoint assume the server role, so both it and reverse-direction §6.2.5 are deferred to 1.1. Other server-initiated operations are outside 1.0 and planned for 1.1. The normative operation inventory below follows KMIP 2.1 Specification §§6.1 (57 client-to-server headings) and 6.2 (5 server-to-client headings); duplicate operation names are shown once per direction.

**Legend and interpretation**

**Testability suffixes in the cells:** `exhaustive matrix measured; see results ledger` means every matching valid matrix row has a live classification or an explicit fixture/setup blocker; it does not mean every row interoperated successfully. `FAIL` and `unsupported probe observed` retain actual incompatibilities even when a test passes by asserting that finding. `rejection test only` means the server explicitly documents that operation as unimplemented. `probe` means published operation support is undocumented; check the results ledger for any live probe. `blocked at KMIP 2.1` marks PyKMIP’s version ceiling. `out of scope 1.0` marks server-initiated operations. `deferred from KMIPKit 1.0` marks Set Endpoint Role, whose OASIS-mandated role transition is incompatible with the client-only 1.0 runtime.

- **Yes¹ / No¹ / Undocumented¹** come from the [Cosmian 5.28.0 KMIP support matrix](https://github.com/Cosmian/kms/blob/5.28.0/documentation/docs/kmip_support/support.md). Its 34 supported KMIP 2.1 table rows represent 35 operation paths because `Set Attribute (Modify)` groups Set Attribute and Modify Attribute. The table above preserves that published grouping while displaying the separate KMIP headings. Separate KMIPKit live tests have independently observed successful typed Set and Modify exchanges; neither statement proves every attribute/object combination.
- **Yes³** means PyKMIP’s [server operation list](https://github.com/OpenKMIP/PyKMIP/blob/master/docs/source/server.rst) names the operation. **Undocumented³** means it is absent from that list, not proof that a request is rejected.
- PyKMIP’s version enum currently exposes KMIP up to 2.0, not 2.1 ([source](https://github.com/OpenKMIP/PyKMIP/blob/master/kmip/core/enums.py)). Therefore PyKMIP is useful as a local KMIP reference server, but it cannot provide a strict KMIP 2.1 positive integration target for KMIPKit 1.0.
- Cosmian KMS 5.28.0 declares KMIP 2.1 support. Its [binary socket listener](https://github.com/Cosmian/kms/blob/5.28.0/documentation/docs/configuration/tls.md) accepts binary KMIP on port 5696, requires TLS and client certificate authentication, and can be restricted to TLS 1.3. This is the relevant path for KMIPKit’s raw TTLV/mTLS transport. The HTTP `/kmip/2_1` endpoint carries **JSON TTLV**, so it is not a substitute for testing KMIPKit’s binary TTLV transport ([API docs](https://github.com/Cosmian/kms/blob/5.28.0/documentation/docs/integrations/openapi.md)).
- The Cosmian 5.28.0 license is [Business Source License 1.1](https://github.com/Cosmian/kms/blob/5.28.0/LICENSE); its terms allow non-production use. Confirm the exact license terms for any redistribution or use beyond local tests.
- KMIPKit 1.0 covers approved in-scope C→S operations. Set Endpoint Role (§6.1.54) is explicitly deferred together with its S→C counterpart (§6.2.5), because §6.1.54 mandates an endpoint-role transition after success. The “Yes” labels remain vendor declarations; the result suffix and per-case matrix ledger identify actual exchanges and failures. All scoped valid case dimensions have been measured or explicitly blocked. Other S→C rows are intentionally outside KMIPKit 1.0.

## Cosmian 5.28.0 exhaustive matrix outcomes

The operation-level success and no-success tables are maintained in the [KMIPKIT-0015 integration report](../../specs/015-cosmian-kms-integration/task-6-report.md#operation-level-interoperability-summary). Their executable-case counts and per-case classifications come from [`capability-matrix.json`](../../tests/integration/cosmian/capability-matrix.json); standards-invalid exclusions were not sent and are excluded from those operation denominators.

The separate probes are outside the advertised-success count: `Adjust Attribute`: malformed_response (Status 1, Reason 4; The typed Adjust Attribute request was sent for Usage Limits Total. Cosmian returned Operation Failed / Invalid Message without Batch Item Operation; KMIPKit rejected the malformed response.); `Ping`: malformed_response (Status 1, Reason 4; Cosmian returned Operation Failed / Invalid Message without the required Batch Item Operation; KMIPKit rejected the malformed response.); `Re-certify`: unsupported (Status 1, Reason 5; The typed Re-certify request for a case-owned registered certificate received a well-formed Operation Failed / Operation Not Supported response.).

The latest complete serial ignored suite ran against the pinned Cosmian image with rustls 0.23.46 and ended with 101 passed and 9 failed test functions after 6,383.81 seconds. Six valid RNG requests and other malformed/error response shapes remain recorded as findings. The current operation-level success and no-success summaries—including refreshed Encrypt, Decrypt, Get, Export, Import, and Register counts—are in the [KMIPKIT-0015 integration report](../../specs/015-cosmian-kms-integration/task-6-report.md#operation-level-interoperability-summary). A targeted follow-up resolved the 50 legacy-PKCS#12 Get/Export response-validation failures by sending the missing vendor format selector; Get now records 797/1,279 and Export 807/1,291 observed interoperable cases. Read the [integration run guide](../../tests/integration/cosmian/README.md) for commands and the [requirement traceability report](../../specs/015-cosmian-kms-integration/traceability.md) for family totals and interpretation.

## Recording an actual result

For future server tests, replace only the matching `Pending` cell with a concise result and link the executable test/evidence. Keep the product build, image/package digest where available, server configuration, TLS version, certificate setup, operation payload, response status/reason, date, and any known workaround in the test report. Record a negative response as a negative interoperability result only when the test expected that server behavior; do not call an unsupported operation “successful” merely because the server returned an error safely.

Suggested result values: `OK` (assertions passed), `FAIL` (unexpected behavior), `SKIP` (not run, with reason), and `N/A` (not in the client release scope). `OK` applies only to the exact recorded case; it does not claim profile conformance or certification.

For KMIPKIT-0039, the Get Constraints (§6.1.22), Get Usage Allocation (§6.1.23), Set Constraints (§6.1.52), and Set Defaults (§6.1.53) result rows remain `Pending` for every server because no live exchange for these operations has been measured. When testing, record the exact KMIPKit commit, server product/build and image or package digest, listener and server configuration, transport and negotiated TLS version, client-certificate setup, operation and request table, response status/reason and delivery state, UTC run date, outcome, and any workaround. The explicit Usage Allocation guard is local client accounting; it is not a server interoperability result. Set Endpoint Role remains outside the 1.0 test scope.

On 2026-10-11, the pinned Cosmian KMS 5.28.0 image was started with the local mTLS test certificates. Separate credential-session probes for Delegated Login (§6.1.12), Login (§6.1.30), and Logout (§6.1.31) sent binary TTLV/TLS requests. Each received Failure/Invalid Message without the Operation field, which OASIS KMIP 2.1 §8.6, Table 399 requires when the request batch item includes Operation. KMIPKit rejected each response after response delivery began and retained its generic TTLV for inspection. These are `FAIL` interoperability results for credential-session operations; they are unrelated to KMIPKIT-0039 and do not change its four still-pending result rows above. PyKMIP's current version enum lists KMIP 2.0 as its latest version and does not list 2.1, so it is not a strict KMIP 2.1 integration target. The two-independent-implementation release gate remains open. The focused live probes are in `crates/kmipkit-client/tests/credential_sessions_cosmian.rs` and remain ignored in ordinary test runs.
